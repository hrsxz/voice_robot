# 提案：流式识别 + 流式执行（voice-streaming）

## Why

`voice-quick-wins` 之后，延迟主要剩下两段：一是松开空格后才开始上传、识别整段录音；二是 LLM 要把整个 JSON 生成完才开始执行。改成边说边识别、边生成边执行之后，第一个动作可以在用户说完之前、或者 LLM 输出完之前就开始。

## What Changes

- 按空格模式改为流式识别：按住空格期间持续把音频送去识别，说话过程中就得到分句结果。
- 流式模式下按分句路由：分句一确定，命中快速通道的就马上按顺序执行；遇到第一个没命中的分句，就把剩下的话交给 LLM，同时告诉 LLM 前面已经执行了哪些动作。
- 流式模式下，识别结果里一出现停止词就立即停止，并清空待执行的命令。
- LLM 改为流式输出、每行一个动作；收到一行就校验一行，合法的马上放进执行队列。
- RobotAgent 新增执行队列：按顺序逐条执行，"停"会清空队列，每条命令都有统一的结果记录。
- 流式识别失败时，自动回退到 `voice-quick-wins` 的整句识别。
- 新增离线回放测试：用录好的音频文件驱动整条链路，不需要每次都真人说话。

## Capabilities

### New Capabilities

- `speech-input`：怎样从麦克风得到用户说的话，包括采集方式、流式识别、一句话何时结束、失败回退、录音的保留。
- `command-execution`：命令进入执行队列后怎样执行，包括顺序、停止清空、结果记录。

### Modified Capabilities

- `voice-command-routing`（由 `voice-quick-wins` 引入）：新增流式模式下的分句路由、流式停止和 LLM 逐行执行。原有的整句模式规则不变，仍然作为回退路径使用。

## Impact

- **代码**：`pc/llm/audio_utils.py`（流式采集）、新增流式 STT 客户端、`pc/llm/llm_client.py`（流式输出）、`pc/llm/intent_parser.py`（逐行解析）、`pc/agent/robot_agent.py`（执行队列）、`pc/voice_to_robot.py`（主循环）、`skills/base.skill.md`（输出格式改为每行一个动作）。
- **依赖**：可能需要 WebSocket 客户端库（看 spike 的结论）。
- **前置条件**：`voice-quick-wins` 先完成（复用它的匹配器、耗时测量和整句回退路径）。
- **局限**：正在执行的动作要等 `hub-protocol-v2` 完成后才能被"停"打断；在那之前，"停"只能清空还没发出的命令。
- **数据保护**：音频在识别期间仍然上传到云端；临时录音在处理完后删除。回放测试用开发者自己的录音或合成语音，不用小朋友的声音。
