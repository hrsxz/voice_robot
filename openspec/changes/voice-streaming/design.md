# 设计：流式识别 + 流式执行

## Context

本改动建立在 `voice-quick-wins` 之上，复用它的严格匹配器、分句拆分、耗时记录和整句识别路径。和本设计相关的现状：

- `RobotAgent.execute_sequence` 一次性接收一个完整列表；`SpikeHub.send` 等 Hub 就绪后才发送。
- Hub 执行动作时是阻塞的，执行期间不读新命令。所以本改动中的"停"只能取消**还没发出**的命令，打断正在执行的动作要等 `hub-protocol-v2`。
- 需求见 specs/，动机见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 说话过程中就开始识别，并让第一个动作尽早开始执行。
- 执行队列成为快速通道、LLM（以后还有 Realtime）共同的唯一入口。

**Non-Goals:**
- 唤醒词模式下的流式识别（`voice-input-modes`）。
- 打断正在执行的动作（`hub-protocol-v2`）。

## Decisions

### D1 流式识别方案：云端实时转写为主，按停顿分段
首选 **A：OpenAI 实时转写（WebSocket）**。按住空格期间持续推送 16 kHz PCM16 音频，由服务端按短停顿（约 300–400 ms）切分语段，每个语段说完就给出文字；松开空格时提交最后一段。
- 备选 **B：本地 VAD 分段 + 每段调用一次普通转写接口**。复用现有的 webrtcvad 和整句接口，简单，也不绑定供应商；缺点是最后一段要等上传和识别，比 A 慢约 0.3–0.5 s。
- 第 1 组任务先做一个 spike，验证 A 能否在按住期间给出分段结果，并实测延迟。达不到 `speech-input` 的目标时改用 B。两种方案都满足同一份 spec，后面的路由和执行不受影响。
- **Spike 结论（见 spike.md）：采用 A**，模型用 `gpt-4o-transcribe`，加上简体中文和命令词的 prompt，服务端 VAD 静音阈值 300 ms。实时接口只支持 24 kHz，所以流式模式按 24 kHz 采集；整句识别的回退路径也使用同样的 prompt（否则会混入繁体字，快速通道认不出来）。

### D2 什么算"分句确定"
语段结束时，先按原文的标点和连接词把这个语段拆成分句（拆完再逐句规范化，因为规范化会去掉标点）：除最后一个分句外，前面的都算确定。语段的最后一个分句：**如果它本身已经能完整匹配**（例如"向前走五十厘米"），立即确定；否则先挂起，等下一个语段来了拼在一起再判断（应对"向前走 [停顿] 三十厘米"），或者在松开空格时确定。

（实现时的修正：最初的设计是"最后一个分句一律等下一个语段"，但实际说话时每个停顿之间往往只有一个分句，那样第一个动作要等第二句识别出来才会执行，提前执行就失去了意义。）

用户如果一口气说完不停顿，就没有提前执行的效果，但结果仍然正确。

### D3 分句路由状态机
每句话有两种状态：**快速**（初始）和 **LLM**。
- 快速状态下，每确定一个分句就去匹配：命中就放入执行队列；没命中就切换到 LLM 状态，并把这个分句记为"交给 LLM 的起点"。
- LLM 状态下继续收集后面的文字，直到这句话结束；然后把"剩余文字 + 已执行动作列表"交给 LLM。
- 在任何状态下，中间识别结果里一出现停止词，就立即停止（见 D5）。

### D4 LLM 每行输出一个动作（NDJSON）
`skills/base.skill.md` 的输出规范改成每行一个 `{"action":..., "args":...}`。`LLMClient` 开启流式输出，按换行切分，每凑齐一行就交给解析和校验，然后放入队列。
- 备选：用流式函数调用（tool calling）。否决：参数是一块一块到达的，拼接复杂，而且绑定供应商；NDJSON 简单，换模型也能用。Realtime 链路（`voice-realtime-pipeline`）那边再用函数调用。

### D5 停止词检测在中间结果上做
对识别的中间结果做停止词检测，而不是等分句确定之后再判断，换取更短的反应时间。检测到后：清空队列 → 发出 `stop` → 丢弃这句话剩下的内容。

### D6 执行队列
RobotAgent 内部用一个 `asyncio.Queue` 加一个后台执行任务：取出一条 → 校验 → 发送 → 记录结果。停止操作会清空队列，并把被清掉的命令标为"被停止取消"。原来的 `execute_sequence` 改成"把整个列表依次入队，再等它们执行完"，这样整句路径的行为不变。

### D7 回退
流式连接异常时，用已经采集到的整段音频走 `voice-quick-wins` 的整句识别和整句路由。音频在本地一直完整保留，直到这条命令处理完再删除，所以回退时不会丢内容。

### D8 回放测试
测试工具可以用 WAV 文件代替麦克风，按实时速度推送音频，Hub 用 simulate 模式。这样流式行为可以重复测试，也能自动对比延迟。测试录音用开发者自己的声音或合成语音。

## Risks / Trade-offs

- [依赖停顿分段：一口气说完的句子享受不到提前执行] → 结果仍然正确；在 README 里提示分句之间稍作停顿。
- [中间结果里的停止词误触发，比如"停车场"] → 宁可多停：安全优先，停错了重新说一遍就行。
- [提前执行后，用户想改口来不及] → 说"停"可以清空队列；`hub-protocol-v2` 之后还能打断正在执行的动作。
- [实时转写的费用和接口变动] → 方案 B 作为现成的替代方案。
- [LLM 不遵守每行一个动作的格式] → 解析不了的行会被拒绝并记录；整句结束时如果一个动作都没解析出来，就提示"无法识别"。

## Migration Plan

- 流式识别作为按空格模式的默认实现，保留一个参数可以切回整句识别。
- Hub 程序不用改。
- 回滚：关闭流式参数，或者 git revert。

## Open Questions

- 服务端分段的停顿阈值：spike 选定 300 ms；如果实车测得松开后的延迟仍然高于 0.5 s，再试 200 ms。不影响方案本身。
