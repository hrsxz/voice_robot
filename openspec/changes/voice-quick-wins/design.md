# 设计：语音快速见效

## Context

现在的链路（`pc/voice_to_robot.py`）：录音 → `AudioClient.transcribe_openai`（每次新建同步客户端）→ `LLMClient.generate`（提示词里塞了 4 个 skill 文件的完整 frontmatter，约 11.6 KB）→ `intent_parser` → `intent_mapper` → `RobotAgent.execute_sequence` → `SpikeHub.send`。

和本设计相关的现状：

- `intent_parser._fallback_steps_from_text` 按"关键词是否出现"来猜动作（"左夹子抬起来"会被判成 `left`），不支持中文数字，也不认"夹子"这种说法。LLM 不可用时，`LLMClient.generate` 会原样返回输入文本，交给这套规则去猜。
- `SpikeHub.send` 每发一条命令前都要等 Hub 发 `rdy`，固定最多等 3 秒；而 Hub 是动作做完才发 `rdy`，所以 3 秒以上的动作后面接任何命令都会超时。
- Hub 只在动作**完成后**才回复，现有协议里 PC 看不到"动作开始"这个时刻。

动机见 proposal.md，需要满足的行为见 specs/。

## Goals / Non-Goals

**Goals:**
- 不改 Hub 程序，只改 PC 端。
- 快速通道作为 `LLMClient` 前面的一道独立判断，RobotAgent 仍然是唯一的校验和下发出口。
- 有可靠的耗时数据，作为 `voice-streaming` 和 `voice-realtime-pipeline` 的对比基准。

**Non-Goals:**
- 流式识别和流式执行（`voice-streaming`）。
- 动作中途打断、Hub 回复格式升级（`hub-protocol-v2`）。
- 唤醒词模式的优化（`voice-input-modes`）。

## Decisions

### D1 新建严格匹配器，不在旧的关键词解析上修补
用正则句式表逐条描述每种动作的说法（比如"(向|往)?前(进|走)? <数值> <距离单位>"），一个分句必须**整体**匹配某个句式才算命中。句式来源是 docs 第 1–3 级的例句加上 skills 的 triggers。
- 备选 A：修补 `_fallback_steps_from_text`。否决：包含式匹配的根本问题是关键词之间会互相抢，补丁只会越打越多。
- 备选 B：每次都走 LLM。否决：这正是要解决的延迟问题。

### D2 中文数字转换自己实现
支持 0–9999，包括"两""十五""一百二十"，小数四舍五入；单位支持 厘米 / 公分 / cm / 米 / m / 度 / °。
- 备选：引入 `cn2an` 库。否决：需求很小，不值得多一个依赖。

### D3 路由放在 VoiceController 里，调用 LLM 之前
`input_text` 先交给匹配器：如果所有分句都命中，就直接生成现有的 `{"sequence": [{"cmd": ...}]}` 格式，交给 `RobotAgent.execute_sequence`；否则走原来的 LLM 链路。两条路最后都经过 RobotAgent 的技能规则校验。加一个快速通道开关参数（默认开），方便对比。

### D4 离线兜底改用严格匹配器（BREAKING）
LLM 不可用时，不再把原文交给关键词解析去猜，而是只用严格匹配器的结果；没命中就提示"无法识别"。`_fallback_steps_from_text` 不再出现在执行路径上，依赖它的旧测试要按新行为调整。

### D5 急停规则
整句只由停止词组成（可以带"啊""吧"之类的语气词或重复）→ 立即发送 `stop`。停止词出现在多步命令的某个分句里 → 当作普通的 `stop` 步骤。这样不会把"前进30厘米然后停止"误判成急停而丢掉前进。

### D6 耗时记录
每条命令建一个计时记录对象，沿着链路依次打点：录音结束、STT 完成、路由/LLM 完成、BLE 发出、Hub 完成。命令结束后输出一行汇总，可选追加写入 JSONL 文件（通过参数或环境变量开启）。
- 在现有协议下，"Hub 确认"指的是 **Hub 报告动作完成**；用户感觉到的延迟终点用"BLE 发出"近似（Hub 收到后几十毫秒内就开始动）。`hub-protocol-v2` 会增加明确的"开始执行"确认。

### D7 就绪等待超时按预计时长计算
SpikeHub 记住上一条发出的命令，按它的预计时长决定下一次等 `rdy` 的超时：超时 = 预计时长 × 1.5 + 2 s，最少 3 s。预计时长按动作类型估算：直行用距离 ÷ 速度，转向用角度 ÷ 角速度，夹爪用固定值，巡线用距离 ÷ 巡线速度。速度先取保守值写成常量，之后用耗时日志里的"Hub 完成"数据校准。

### D8 通信失败后快速失败
RobotAgent 执行序列时，一旦遇到 Hub 通信异常（超时、断开、写入失败），剩下的命令一律跳过，并标记"因通信失败跳过"。参数校验不通过的命令仍然保持原来的行为：跳过这一条，继续执行后面的。

### D9 STT 和 LLM 的小优化
- STT：用一个复用的 `AsyncOpenAI` 客户端；按空格录音改为 16 kHz 单声道 int16。
- LLM：提示词改成从 registry 生成的紧凑动作表（动作名、参数、范围）+ base 规则 + 3–5 个示例；限制最大输出 token 数；推理强度做成可配置项，模型不支持时就不传这个参数。

## Risks / Trade-offs

- [匹配器太严，命中率低，提速有限] → 耗时日志会记录路由类型，按命中率补充句式。
- [中文数字边界情况，比如"两百五""二十五点五"] → 单元测试覆盖，小数四舍五入。
- [STT 输出的写法多种多样，比如"30 cm""三十公分"] → 单位同义词都支持，空格先规范化掉。
- [按"后"拆句时误伤"往后退""后退"] → 只在"数值+单位"后面的"后"处拆分。
- [速度估计不准：太短会误报超时，太长会让真正的故障发现得慢] → 留足余量，再用实测数据校准。
- [精简提示词后 LLM 准确率下降] → 用一组固定例句对比精简前后的解析结果。
- [BREAKING：离线时以前能"猜对"的一些说法现在会被拒绝] → docs 里的说法都由快速通道覆盖。

## Migration Plan

- 只改 PC 端，Hub 程序不用重新下载。
- 快速通道可以用参数关掉，退回到原来的 LLM 链路。
- 回滚：git revert 本改动的提交。
