# 设计：Realtime 语音链路

## Context

- 前置改动提供了：执行队列和停止清空（`voice-streaming`）、启动参数和本地唤醒（`voice-input-modes`）、可打断的停止（`hub-protocol-v2`）、耗时记录（`voice-quick-wins`）。
- 技能 registry 已经有每个动作的 `value_type`、`arg_key`、`min` / `max`，可以直接生成工具定义。
- 需求见 specs/，动机见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 和 stream 链路共用执行队列、校验和耗时记录，只替换"语音 → 命令"这一段。
- 把实时接口的细节封装在一个模块里，接口变了只需要改这一处。

**Non-Goals:**
- realtime 链路里的本地快速通道（中间没有文字，也就没有快速通道，这正是两条链路要比较的地方）。
- 模型用语音回答（只要动作调用和简短文字，省钱也省时间；语音播报以后再加）。

## Decisions

### D1 会话接口
使用 OpenAI 实时接口（WebSocket）。音频按接口要求的格式重采样后推送（以实现时的官方文档为准）。回复只要文字和函数调用，不要语音。会话里同时打开输入转写，用于停止检测和调试日志。

实现时确定（2026-11-13，openai SDK 2.43）：24 kHz PCM16，`output_modalities: ["text"]`，转写用和 stream 链路相同的 `gpt-4o-transcribe` + 简体中文 prompt。默认模型 `gpt-realtime-mini`（`--realtime-model` 可换）：`gpt-realtime`、`gpt-realtime-mini`、`gpt-realtime-2` 在合成录音上结果相同、每步延迟相近，mini 最便宜（见 measurements.md）。

### D2 每个动作一个工具
从 registry 为每个动作生成一个函数，比如 `forward(distance_cm: int, 0–10000)`、`gripper_left_pos(angle_deg: int, 0–90)`，无参动作的参数为空。会话指令简短说明机器人的角色和规则（中文）：只用工具表达动作；听不懂时用一句简短文字说明。
- 备选：一个 `move(action, args)` 大工具。否决：枚举加条件参数对模型来说更难用，校验也更绕。

### D3 一句话的边界
- 按空格：关闭服务端的轮次检测，松开空格时手动提交。
- 唤醒词：打开服务端 VAD 轮次检测，静音阈值沿用 `voice-input-modes` 的配置（默认 700 ms）。
- 实现时补充：服务端 VAD 设为 `create_response: false`、`interrupt_response: false`，回复一律由程序请求。这样同一时间只有一条回复在生成，前一句还在生成时又说了一句，新的一句排队（见 D4）。

### D4 执行动作调用
某个函数调用的参数接收完毕 → 解析 → 按技能规则校验 → 放进执行队列 → 立即给模型回一个函数结果（"已入队"或"被拒绝：原因"），不等动作执行完。这样模型可以继续给出后面的调用。

实现时发现：三个实时模型**每次回复都只给一个函数调用**（"前进50厘米然后右转90度"第一次回复只有 `forward 50`）。所以回完函数结果后，程序要再请求一次回复，模型才给出下一个调用，直到某次回复不再调用工具为止（通常是一句"已完成"，不打印）。每一步约 0.45 秒；第一个动作入队后小车已经在动，后面的调用和执行同时进行。为防止模型陷入循环，一句话最多 24 次调用。

函数结果里带上"这句话第几个动作"（"已入队（这句话第 3 个动作）"），帮模型数"一共做四次"。

每句话独立：开始为一句话请求回复之前，删掉会话上下文里之前几句话的条目（`keep_context=False`，默认）。实测保留上下文时，同一会话里第二次说"向前走三十厘米，再左转九十度，一共做四次"，`gpt-realtime-mini` 两轮都只做了 3 遍；删掉后连续 3 次都对。这和 stream 链路（每句话独立交给 LLM）一致，也避免每次请求的音频 token 越积越多。代价是不能说"再做一次"这类依赖上一句的话（stream 链路同样不支持）。

校验比 stream 链路的 LLM 输出更严格：不认识的动作、缺参数、多余参数、类型不对、超范围一律拒绝（LLM 文字输出那边会宽松纠正，比如枚举值不对时用默认值）。被拒绝的调用也记在这句话的执行汇总里。

### D5 停止保障
两路检测，谁先到就用谁：（1）会话输入转写的中间文字；（2）`voice-input-modes` 的本地识别（主要用于唤醒模式）。检测到停止词就清空队列、发出 stop，同时取消模型当前这一轮回复。

实现时补充：录制的事件显示，"停"的转写约 0.46 秒到达，而 `gpt-realtime-mini` 给出 `stop` 调用要 0.6–1.7 秒，所以转写这一路确实更快。急停后，正在生成和排队的所有回复都作废，之后到达的函数调用一律忽略（接口在取消时也会发出参数不完整的调用事件）。模型自己调用 `stop` 也按急停处理，不进执行队列。转写同样要过滤提示词回显（`voice-input-modes` 发现的问题）。

### D6 会话生命周期
- 按空格：程序启动时建立会话并保持连接，只在按住空格时发送音频；会话到达时长上限时自动重连。
- 唤醒词：唤醒后建立会话，连续 20 秒没有人声就关闭。
- 实现时补充（唤醒词）：窗口内不再按本地切句一句一句处理，而是从唤醒词所在的片段开始，把窗口内的**全部**音频按顺序连续推给会话（服务端 VAD 需要看到句末的静音才能判断说完）；会话还没连上时音频先排队。本地切句只用来给窗口续时，以及在窗口内本地检测"急停"。窗口关闭后不再推送任何音频。

### D7 失败回退
建立会话失败、或者中途断开且重连失败时，提示原因，然后把链路切换到 stream（使用同一个输入方式）。切换以后在终端标明当前用的是哪条链路。

实现时补充：按空格模式下正好在断开时说的那句话，用完整录音做整句识别；唤醒模式下唤醒后连不上会话时，已经排队的音频（从唤醒词开始）也用整句识别处理。重连成功（上下文丢失）时，正在处理的句子记为失败，提示重说。

### D8 对比工具
同一批 WAV 录音（Hub 用 simulate 模式）分别跑 stream 和 realtime 链路，输出每条命令的识别结果、动作序列是否正确，以及延迟的中位数对比表。

## Risks / Trade-offs

- [费用高于 stream 链路] → 只在选择 realtime 时使用；按空格模式下没按键就不发音频。
- [接口还在演进，事件格式可能变化] → 封装在一个模块里，用录制的事件做测试夹具（fixture）。
- [模型调用了错误的工具或参数] → 统一校验；对比工具会统计正确率。
- [唤醒窗口期间音频持续上传] → 20 秒空闲关闭；文档里写明数据保护注意事项。
- [前一句的调用还在生成时又说了一句] → 新的一句立即提交（这样转写里的"停"能马上生效），但回复排队；前一句继续生成时模型已经能"听到"新的一句，可能提前执行新一句的动作，轮到新一句时再重复一次。只有快速连续说多步命令时才会遇到；实车实验 5-1 里观察。
- [依赖单一供应商] → stream 链路作为常备方案，失败时自动切换过去。

## Migration Plan

- 新增链路，默认链路不变（stream），需要显式选择 realtime。
- 回滚：不选 realtime 就不会用到；必要时 git revert。
