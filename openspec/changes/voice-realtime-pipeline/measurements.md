# 测量记录：voice-realtime-pipeline

测量日期：2026-11-13。全部用合成语音（`scripts/make_test_audio.py` 生成的 18 条 docs 第 1–3 级例句和混合句），Hub 用 simulate 模式。真人声音和实车的验证见 `docs/experiments.md` 的实验 5-1 到 5-3（任务 4.2）。

## 1. 接口行为（spike，`scripts/record_realtime_events.py`）

用同一组录音和工具定义，比较三个实时模型（只要文字和函数调用，按空格方式手动提交）：

| 模型 | "前进50厘米然后右转90度" | "前进30厘米再左转90度，一共做四次" | 每一步间隔 |
|---|---|---|---|
| `gpt-realtime` | 正确 | 正确（8 个调用） | 约 0.45–0.5 s |
| `gpt-realtime-mini` | 正确 | 正确（8 个调用） | 约 0.45–0.5 s |
| `gpt-realtime-2` | 正确 | 正确（8 个调用） | 约 0.6 s |

- **三个模型每次回复都只给一个函数调用**。要回函数结果、再请求一次回复，模型才给出下一个；最后一次回复是一句"已完成"之类的文字（不打印）。所以多步命令的"全部动作确定"时间约等于 `0.45 s × 动作数`，但第一个动作入队后小车已经在动。
- 选 `gpt-realtime-mini` 作默认：结果和延迟与 `gpt-realtime` 相同，价格低很多。
- "停"：转写的第一个字约 0.46 s 到达；`gpt-realtime-mini` 给出 `stop` 调用要 0.6–1.7 s。停止检测走转写这一路是对的（设计 D5）。
- 录下来的事件放在 `tests/fixtures/realtime/`，作为会话客户端单元测试的夹具。

## 2. 两条链路对比（任务 4.1，`scripts/compare_pipelines.py`）

18 条录音 × 2 轮，每条录音按实时速度推送，"说完"定义为最后一块音频送出（相当于松开空格）。

- **首个动作**：说完 → 第一个动作放进执行队列。stream 命中快速通道时，第一个动作在说完之前就执行了，所以是负数。
- **全部动作**：说完 → 这句话的最后一个动作确定（stream：快速通道在松开时就确定了，记为 0；交给 LLM 时是 LLM 输出完；realtime：模型不再调用工具）。

最终代码的结果（`logs/compare_final2.txt`）：

| 链路 | 条数 | 正确 | 首个动作中位数 | 全部动作中位数 |
|---|---|---|---|---|
| stream | 36 | 33/36 | −1048 ms | 120 ms |
| realtime（`gpt-realtime-mini`） | 36 | 34/36 | 816 ms | 1528 ms |

按句子类型（中位数，stream / realtime）：

| 类型 | 首个动作 | 全部动作 |
|---|---|---|
| 第 1 级（一个动作，快速通道能识别） | 503 / 864 ms | 374 / 1370 ms |
| 第 2 级（两个动作） | −2671 / 832 ms | 0 / 1871 ms |
| 第 3 级（4–8 个动作） | −9274 / 768 ms | 0 / 2805 ms |
| 混合（"前进三十厘米，然后跳个舞"，后半句要 LLM） | −2260 / 872 ms | 2984 / 1432 ms |

同一天更早的一次完整对比（改指令之前）realtime 的首个动作中位数是 692 ms，第 1 级 680 ms，说明实时接口本身的延迟有 ±100–150 ms 的波动。

**结论**：

- 快速通道能识别的命令（docs 第 1–3 级全部例句），stream 链路明显更快：分句之间稍有停顿，第一个动作在说完之前就执行了；realtime 要等说完再等模型，约 0.7–0.9 s。
- 需要 LLM 的句子，realtime 更快：stream 要"转写 + LLM"两次云端调用（全部动作约 3.0 s），realtime 约 1.4 s。
- 准确率差不多，错的地方不一样（见下一节）。
- 所以 stream 仍然是默认链路；realtime 适合以后句子越来越"自由"、快速通道命中率低的场景（比如改动 8 的任务层）。

## 3. 错误分析和实现中的调整

| 现象 | 原因 | 处理 |
|---|---|---|
| realtime："左夹子抬起来，左夹子放下来，右夹子抬起来，右夹子放下来"，前两个动作做成了两个夹爪一起动（4/4 次） | 模型直接"听"音频，对这条录音开头的"左夹子"听不准；三个模型都有这个问题（`gpt-realtime-2` 3 次对 1 次）。stream 链路的转写模型这句一直是对的 | 工具描述写明"夹子 = 夹爪""只说左/右时只动那一边"，单独的"左夹子抬起来"和"左夹子抬起来，右夹子放下来"都正确；这一句没有再针对性调整，作为 realtime 链路的已知弱点记录下来 |
| realtime："一共做四次"只做了 3 遍（第一次完整对比中 2/2 次） | 同一会话里保留了之前几句话的上下文；全新会话里是对的 | 每句话开始前删掉之前的上下文（设计 D4）；之后 `gpt-realtime-mini` 连续 3 次和完整对比里都正确 |
| realtime："前进三十厘米，然后跳个舞"整句被拒绝（1/2 次） | 指令说"做不到就不调用工具" | 指令改为"能做的照常调用，最后说明哪部分做不了"；之后 4/4 次都先执行了前进 |
| realtime：只说唤醒词时模型回一句"你好，请说出……" | 唤醒词那一段音频也交给了模型 | 指令里写明只有唤醒词时不回复（模型有时仍会回一句，只在终端显示一行，不影响动作） |
| realtime（唤醒模式）：转写和本地识别各报告一次"急停"，发了两次 stop | 两路检测都生效 | 1 秒内只发一次 |
| stream：很短的"停"转写为空（本次两轮都没停） | 实时转写对很短的音频不稳定（`voice-input-modes` 里已经见过提示词回显）；本改动没有修改 stream 链路 | 记录下来；实车实验 1b-1、1c-3 里观察真人说"停"的情况 |
| stream："向左转一百八十度，然后……"漏掉角度 | 转写漏字 | 同上，属于 stream 链路的识别误差 |

## 4. 唤醒词 + realtime 回放（`scripts/replay_wake --pipeline realtime`）

真实 VAD、本地 tiny 模型、真实实时接口、模拟 Hub：

| 片段 | 结果 |
|---|---|
| 聊天（"今天天气真不错…"） | 本地识别 2 个片段，没有唤醒，没有建立会话，上传 0 次 |
| "小蓝小蓝" | 唤醒，建立会话，上传审计日志 1 行（`kind: realtime`） |
| "向前走三十厘米"（窗口内，不说唤醒词） | `forward 30`，首个动作约 0.55–0.9 s |
| "向前走五十厘米，然后向右转九十度" | 服务端在 0.6 s 的停顿处切成两句，按顺序执行 `forward 50`、`right 90`（和 stream 链路的唤醒模式一样，第二句交给模型时不知道第一句） |
| "急停"（窗口内） | 本地识别先报告，162–218 ms 内发出 stop，只发一次 |

## 5. 费用

没有逐条统计。实时模型按音频 token 计费，比"转写 + 文字 LLM"贵；`gpt-realtime-mini` 比 `gpt-realtime` 便宜很多。降低费用的设计：按空格时不按键不上传；唤醒模式 20 秒没人说话关闭会话；每句话开始前删掉之前的上下文，每次请求的输入不会越积越多；会话另外设置了 8000 token 的上下文上限。本次全部对比和回放（约 200 条句子）的费用在几美元以内。
